# seedling-gen CLI

Use this skill when a Go project wants seedling blueprint scaffolding.

`seedling-gen` generates one file marked `// Code generated by seedling-gen. DO NOT EDIT.` containing:

- Go model structs for tables (`sql` and `atlas` only)
- a `Blueprints` struct with one `seedling.Blueprint[T]` field per model, built by `NewBlueprints()`
- deterministic `Defaults` for common scalar fields
- relation definitions such as `seedling.BelongsTo`
- `Insert` / `Delete` callbacks only where the adapter can derive them (GORM, ent, sqlc with matching queries)
- `Register(reg) error` / `MustRegister(reg)` methods that register every blueprint

It does not infer application-specific database calls. A blueprint without a derivable `Insert` leaves it unset, and `Register` fails for that blueprint until hand-written code sets it.

The generated file is rewritten on every run. Never edit it. Put customizations in a separate hand-written file in the same package, which changes the generated blueprints before registering them:

```go
// blueprints.go (hand-written)
func NewRegistry() *seedling.Registry {
    blueprints := NewBlueprints()
    blueprints.User.Insert = insertUser // project DB call
    blueprints.User.Traits = map[string][]seedling.Option{
        "admin": {seedling.Set("Role", "admin")},
    }

    reg := seedling.NewRegistry()
    blueprints.MustRegister(reg)
    return reg
}
```

## Installation

- Homebrew (macOS / Linux): `brew install --cask mhiro2/tap/seedling-gen`
- Go toolchain: `go install github.com/mhiro2/seedling/cmd/seedling-gen@latest`

## Input selection

Choose exactly one input source. Prefer the strongest source of truth already used by the target project.

1. `sqlc.yaml`
   Use `sqlc --config`. Config v1 and v2 are supported, and `schema` may be a file, a directory, or a list. The config must contain exactly one Go-generating entry; if it has several, split it or fall back to manual mode (`--dir` + `--import-path` + schema file).
2. GORM model directory with `gorm` struct tags
   Use `gorm --dir` and `--import-path`.
3. ent schema directory with `Fields()` / `Edges()`
   Generate the Ent client first, then use `ent --dir` and `--import-path`. The generated package is the source of truth for field and builder names.
4. Atlas HCL schema
   Use `atlas`.
5. SQL DDL files
   Use `sql` and pass a schema file path.

## Workflow

1. Inspect the repository and find the primary schema source.
2. Pick the output package and file path.
3. Run `seedling-gen` with one subcommand.
4. If the schema mapping is uncertain, run the same command with `--explain` first to inspect parsed tables, keys, and inferred relations. Use `--json` when the output needs to be consumed by tooling.
5. Review generated relation names, optional relations, and composite key handling.
6. Review generated `Defaults` values and confirm they do not conflict with unique or business constraints.
7. Write or update the hand-written file that sets missing `Insert` / `Delete` callbacks, wraps `Defaults`, adds `Traits`, and calls `MustRegister`. Do not edit the generated file.
8. Run formatting and tests in the target repository.

Use `--out` when writing a file. The CLI writes atomically, so failures do not leave partial output behind. Add `--check` to the same command in CI to fail when the generated file is missing or stale after a schema change.

## Commands

```bash
# SQL DDL
seedling-gen sql \
  --pkg testutil \
  --out internal/testutil/blueprints/seedling_gen.go \
  schema.sql

# sqlc config
seedling-gen sqlc \
  --config sqlc.yaml \
  --pkg testutil \
  --out internal/testutil/blueprints/seedling_gen.go

# sqlc manual mode
seedling-gen sqlc \
  --dir ./internal/db \
  --import-path github.com/acme/app/internal/db \
  --pkg testutil \
  --out internal/testutil/blueprints/seedling_gen.go \
  schema.sql

# GORM
seedling-gen gorm \
  --dir ./internal/models \
  --import-path github.com/acme/app/internal/models \
  --pkg testutil \
  --out internal/testutil/blueprints/seedling_gen.go

# ent
seedling-gen ent \
  --dir ./ent/schema \
  --import-path github.com/acme/app/ent \
  --pkg testutil \
  --out internal/testutil/blueprints/seedling_gen.go

# Atlas HCL
seedling-gen atlas \
  --pkg testutil \
  --out internal/testutil/blueprints/seedling_gen.go \
  schema.hcl
```

## Notes

- `--pkg` sets the generated Go package name.
- `--out` writes atomically to the destination file.
- `--check` compares freshly generated code with the `--out` file without writing it, and exits non-zero when the file is missing or out of date. It requires `--out` and cannot be combined with `--explain` or `--json`.
- `--explain` prints parsed schema/model metadata plus inferred blueprint relations instead of generated code.
- `--json` prints the same diagnostic report as JSON.
- `--dialect` is available on `sql` and `sqlc` and defaults to `auto` when omitted. Supported values are `auto`, `postgres`, `mysql`, and `sqlite`. It selects string and comment syntax (dollar quotes, `E'...'`, and nested comments for `auto`/`postgres`; backslash escapes and `#` comments for `mysql`) and primary key nullability (SQLite keys may be NULL unless they are a non-`DESC` `INTEGER PRIMARY KEY` or the table is `WITHOUT ROWID`); pass the real dialect when the schema relies on either.
- `atlas` reports an error for a `foreign_key` block it cannot resolve (missing `columns` or `ref_columns`, a column the table does not declare, mismatched column counts, or references to more than one table) instead of dropping the relation.
- `--import-path` must be a full Go import path.
- The `ent` import path must resolve to compilable entc output. `seedling-gen` reads exact field, mixin, setter, lifecycle, and ID signatures so custom acronyms are preserved and missing or incompatible generated signatures are rejected.
- Generated `Defaults` fill common scalar fields deterministically, but skip primary keys (including GORM's untagged `ID` convention), relation foreign keys, and unsupported custom types. Fields promoted from an embedded `gorm.Model` are set through the embedded struct literal.
- Customize through the `Blueprints` fields in hand-written code: assign `Insert` / `Delete`, wrap the generated `Defaults` (`base := b.User.Defaults; b.User.Defaults = func() User { u := base(); u.Name = "alice"; return u }`), set `Traits`, or `append` to `Relations`. Adding columns or relations and regenerating then needs no repair to that code.

## Troubleshooting

- **GORM model parse failure** — Ensure `--import-path` points to the full Go import path of the models package. If unexported fields or custom types cause issues, check that the package compiles independently with `go build`.
- **FK or relation not detected** — `seedling-gen` infers relations from foreign key constraints. If the schema lacks explicit FK definitions (common in MySQL or older DDL), append the missing `Relation` entries to the blueprint's `Relations` in hand-written code.
- **Composite key mismatch** — Verify that `LocalFields`, `RefFields`, and `RemoteFields` in the generated `Relation` list their columns in matching schema order.
- **Generated defaults violate constraints** — Override generated `Defaults` when the schema expects unique values, enumerated business values, or non-scalar custom types that the generator intentionally leaves untouched.
- **ent edge not mapped** — A singular edge (`Unique` or `Required`) needs `.Field(...)` on whichever schema holds the FK column, and the named field must also appear in that schema's `Fields()`. The opposite side of a one-to-one needs nothing, since ent does not allow `.Field(...)` there. M2M edges via join tables require manual `ManyToManyRelation` definitions.
- **ent generated signature mismatch** — Run Ent generation again and ensure `--import-path` names that generated package. seedling-gen stops when schema fields, builder setters, lifecycle methods, or ID types differ from the compiled Ent output.

## Verification checklist

- The chosen adapter matches the repository's real schema source.
- The generated package path and import path are correct.
- Required relations are present and optional relations were not forced accidentally.
- Composite keys and foreign keys map to the expected local and remote fields.
- Generated `Defaults` are acceptable for the target schema, or have been replaced where uniqueness and domain rules require it.
- Every blueprint without a generated `Insert` gets one in hand-written code; otherwise `Register` reports it.
- The generated file is unedited, and `--check` passes with the same flags.
